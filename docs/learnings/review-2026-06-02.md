# Code Review: opencode-skill-hush

**Date:** 2026-06-02
**Files:** src/index.ts, src/hooks/skill.ts, src/hooks/command.ts, src/hooks/chat.ts, src/hooks/__tests__/*.test.ts, README.md, AGENTS.md
**Focus:** all (security, performance, correctness, maintainability)
**LOC:** 145 source / 224 test / 369 total

## Findings

### [CRITICAL] Stale documentation — README and AGENTS.md omit chat.message hook

- **File:** README.md:94-104, AGENTS.md:9
- **Issue:** The `chat.ts` handler (hooking `chat.message`) was added in commit `d332501` but the README's "Structure" section and "How it works" table still list only 2 hooks. The AGENTS.md also omits `chat.ts` from its structure listing. Anyone reading the docs will believe the plugin only operates on `tool.execute.after` and `command.execute.before`, missing the `chat.message` suppression entirely.
- **Fix:** Add `src/hooks/chat.ts` to both documentation sections. Update the "How it works" table to include the `chat.message` row. The README's install example for local plugins also references `src/index.ts` but should reference `dist/index.js` per plugin conventions.

### [CRITICAL] `as any` type erasure silences real type errors in production code

- **File:** src/hooks/chat.ts:23, src/hooks/command.ts:10-11
- **Issue:** `output.parts[i] as any` (chat.ts:23) and `(p: any)` parameter annotations (command.ts:10-11) completely bypass TypeScript's type checker. If the `Part` type contract changes upstream (e.g., `text` field renamed, `type` field narrowed), these files will compile cleanly but fail at runtime. Three of the 4 `any` casts are in production hooks, not tests.
- **Fix:** Import the `Part` type from `@opencode-ai/sdk` (already imported in command.ts and chat.ts) and use proper type narrowing. Replace `(p: any)` with `(p: Part)` and filter on the narrowed type. Replace `as any` with type guards or type-safe assertions.

### [MEDIUM] Silent error swallowing in logging — `.catch(() => {})` hides failures

- **File:** src/hooks/command.ts:26, src/hooks/chat.ts:44
- **Issue:** Both `client?.app?.log()` calls are followed by `.catch(() => {})`, which silently discards all errors. If the logging API changes signature, throws on invalid payloads, or the host app's logging infrastructure is broken, there is zero visibility into the failure. The plugin will silently stop logging with no way to diagnose the issue.
- **Fix:** Log to `console.warn` as a fallback — or at minimum log the error class/message: `.catch(e => { if (typeof process !== 'undefined') process.stderr.write?.(`[hush] log failed: ${e}\n`) })`. This preserves the non-crashing intent while providing diagnostic signal.

### [MEDIUM] False-positive risk in `isCommandTemplate` heuristic

- **File:** src/hooks/chat.ts:6-12
- **Issue:** The detection heuristic requires text >= 50 chars, starts with `# heading`, and contains `## ` somewhere in the body. This matches any markdown with H1 + H2 structure — including legitimate user messages written in markdown. A user who writes a long markdown-formatted message will see it silently replaced with `[Command: Their Heading]]`. There is no escape mechanism, no allowlist, and no per-command opt-out.
- **Fix:** At minimum, tighten the heuristic. Consider: (1) requiring the H1 to match a known command prefix pattern like `/`, (2) checking for `<skill_content` tags in the content body, (3) adding an `allowCommands` / `blockCommands` option for user control, or (4) only suppressing parts that originate from the plugin's own `command.execute.before` handler (check `synthetic` marker first, which is already done — the real risk is collision with natural user markdown).

### [MEDIUM] Unconditional computation in command handler when client is undefined

- **File:** src/hooks/command.ts:8-11
- **Issue:** `beforeLen` and `beforePreview` are always computed even when `client` is undefined and the `client?.app?.log()` call will short-circuit to `undefined` (no-op). In tests, `createCommandBeforeHandler()` is called without a client, meaning this string processing runs purely for the side effect of being discarded. Wasted work is minor, but it signals unclear intent — a reader must trace the optional chain to understand that this code path is dead when client is absent.
- **Fix:** Guard the computation behind `if (client)`:
  ```typescript
  if (client) {
    const beforeLen = output.parts.length
    const beforePreview = output.parts ...
    client.app.log({ ... }).catch(() => {})
  }
  ```

### [MEDIUM] Zero test coverage for client logging code paths

- **File:** src/hooks/__tests__/command.test.ts, src/hooks/__tests__/chat.test.ts
- **Issue:** All 9 tests across both files call handlers without a `client` parameter. The `client?.app?.log()` code path is never exercised by tests. Any bug in the log message format, payload structure, or error handling will not be caught by the test suite.
- **Fix:** Add at least one test per handler that passes a mock `client` object with a spy `app.log()`, verifying the log call is made with the expected payload shape.

### [MEDIUM] README local plugin reference points to TypeScript source

- **File:** README.md:62
- **Issue:** The local installation example references `src/index.ts`:
  ```json
  "plugin": ["/path/to/opencode-skill-hush/src/index.ts"]
  ```
  Per project convention (AGENTS.md: "Path-based plugins must reference compiled `.js` entry points"), this should reference `dist/index.js`. Pointing at the TypeScript source will fail at runtime since OpenCode's plugin loader expects compiled JS.
- **Fix:** Change to `"/path/to/opencode-skill-hush/dist/index.js"`.

### [LOW] Pervasive `as any` in test files weakens type contract testing

- **File:** All 3 test files (21 `as any` occurrences total)
- **Issue:** Every handler invocation uses `input as any, output as any`. This means the tests bypass the actual type signatures of the hooks. If the OpenCode plugin API changes the shape of `input` or `output` (e.g., removing `args`, renaming `parts`), the tests will still compile and pass with stale shapes, giving false confidence.
- **Fix:** Create typed test fixtures that satisfy the actual hook input/output interfaces. Use `satisfies` or explicit type annotations so type mismatches surface at test-authoring time.

### [LOW] Inconsistent Part construction between command handler and chat handler

- **File:** src/hooks/command.ts:29-36 vs src/hooks/chat.ts:46-51
- **Issue:** The command handler constructs a completely new `Part` object with explicit fields (`id: ""`, `sessionID: input.sessionID`, etc.) and uses `satisfies Part`. The chat handler spreads the original part (`...part`) and overrides only `text` and `synthetic`, then casts with `as Part`. These two approaches have different implications: the command handler discards all original metadata; the chat handler preserves it. This inconsistency makes it harder to reason about what data survives suppression.
- **Fix:** Choose one approach for both handlers. If preserving metadata is desired (it likely is — the chat handler approach is better), refactor the command handler to spread the original part style too. If a clean replacement is desired, refactor the chat handler to use explicit construction.

### [LOW] `argsPreview` in command handler logs user command arguments

- **File:** src/hooks/command.ts:21
- **Issue:** The log payload includes `argsPreview: (input.arguments ?? "").slice(0, 60)`, which captures the first 60 characters of whatever the user typed after a slash command. While this is internal logging, not external disclosure, it could contain sensitive content (passwords, tokens, private messages) that the user expected to be visible only in the TUI, not persisted in logs.
- **Fix:** Either remove `argsPreview` from the log payload, or redact it to show only the command name (already available as `input.command`). If debugging requires argument visibility, restrict it to `debug` level rather than `info`.

## Summary

- 2 critical, 5 medium, 3 low findings
- 145 lines of production code, all reviewed
- **Overall assessment:** The plugin's core logic is simple and well-tested for the happy paths. The main risks are (1) documentation drift — the recently-added chat.ts handler is invisible to anyone reading the docs, (2) type safety gaps — `as any` casts in production code will silently break if the plugin API contract changes, and (3) the template detection heuristic could suppress legitimate user messages. The code is functional and the test suite passes, but the type safety and documentation gaps are real maintenance liabilities.
